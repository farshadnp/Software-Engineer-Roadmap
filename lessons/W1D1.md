# W1D1 — چرا API و چرا جداسازی مسئولیت‌ها؟

مرجع: فصل ۳، بخش‌های ۳.۱.۱ و ۳.۱.۲، صفحات چاپی ۳۶–۳۷، صفحات PDF ۷۶–۷۷. برای ادامه: ۳.۴ درباره Broker، صفحه PDF ۸۶. توضیح‌ها بازگویی آموزشی‌اند؛ نمونه زیر کد مستقل آموزشی ماست، نقل کد کتاب نیست.

هدف این نوبت: تفاوت «درخواست HTTP»، «قانون برنامه» و «ذخیره‌سازی» را تشخیص بدهی. کتاب در مثال Book API نقش‌های Exposer، Service و Broker را معرفی می‌کند. API یک قرارداد قابل استفاده توسط client است؛ تعیین می‌کند چه عملی با چه داده‌ای درخواست می‌شود و چه پاسخی بازمی‌گردد. HTTP روش ارتباط است؛ قانون ایجاد Note می‌تواند از کانال‌های دیگری هم فراخوانی شود.

سناریو: کاربر عنوان یادداشت را می‌فرستد. قانون برنامه: عنوان نباید خالی باشد. ذخیره‌سازی: Note در دیتابیس ثبت می‌شود. پاسخ HTTP: مصرف‌کننده پاسخ موفق یا خطای ورودی می‌گیرد.

نمونه زیر فقط بدنه یک endpoint فرضی است. Note، db، نگاشت route و تنظیمات عمداً حذف شده‌اند؛ برنامه مستقل قابل اجرا نیست و اجرای آن ادعا نمی‌شود.

```csharp
app.MapPost("/notes", async (CreateNoteRequest request, AppDbContext db) =>
{
    if (string.IsNullOrWhiteSpace(request.Title))
        return Results.BadRequest("Title is required.");

    var note = new Note { Id = Guid.NewGuid(), Title = request.Title.Trim() };
    db.Notes.Add(note);
    await db.SaveChangesAsync();

    return Results.Created($"/notes/{note.Id}", note);
});
```

این endpoint برای شروع کوچک و قابل فهم است. صرف وجود منطق در endpoint آن را خودکار «بد» نمی‌کند. سؤال طراحی هنگامی جدی می‌شود که یک مسیر دیگر، مثلاً import از فایل، نیز باید یادداشت ایجاد کند و همان قانون عنوان را رعایت کند.

پاسخ اولیه بررسی شد: parse کردن CSV و تفاوت منبع داده درست تشخیص داده شد. روشن شد که نرمال‌سازی و اعتبار عنوان باید برای همه ورودی‌ها در مرز application/service اعمال شود. `BadRequest` و `Created` فقط مفاهیم HTTP هستند.

سؤال ریویو جاری: چرا Service نباید مستقیماً `BadRequest` برگرداند؟ مسیر CSV که HTTP ندارد، خطای همان قانون عنوان را با چه شکل مستقلی دریافت می‌کند؟

قدم بعد پس از پاسخ: نشان‌دادن جداسازی کوچک HTTP/Service/Storage و مقایسه قبل/بعد؛ توضیح هزینه لایه و interface اضافی و اینکه The Standard انتخاب معماری کتاب است، نه الزام ASP.NET. هنوز این بخش تدریس و تسلط آن تأیید نشده است.

وضعیت: سؤال اول ارائه شده؛ پاسخ و ارزیابی دریافت نشده. زمان واقعی مطالعه کاربر نامعلوم.

## شاهد اجرایی EF Core generated values - ۲۰۲۶-۰۹-۰۸

پروژه `tmp/ef-generated-values` با .NET 10.0.101، EF Core SQLite 10.0.2 و SQLite in-memory اجرا شد. Entity قبل از save دارای `Id=0`، `CreatedAt=DateTime.MinValue` و state=Added بود. SQL واقعی `INSERT ... RETURNING "Id", "CreatedAt"` اجرا شد. بعد از `await SaveChangesAsync()` همان reference (`ReferenceEquals=True`) دارای `Id=1`، زمان تولیدشده دیتابیس و state=Unchanged بود؛ affected entries برابر ۱ شد. این شاهد رفتار mapping/provider پیکربندی‌شده است، نه تضمین برای هر property/provider. پکیج SQLite native کش‌شده هنگام build هشدار امنیتی NU1903 داشت؛ این پروژه فقط آزمایش محلی است و dependency آن نباید بدون ارتقا وارد محصول شود.

## نکته کدریویو: دو نوع validation

- Boundary validation: آیا JSON قابل parse است، ستون CSV وجود دارد و نوع یا قالب داده درست است؟ متعلق به adapter همان ورودی است.
- Application/domain validation: آیا Note با عنوان خالی اصولاً مجاز است؟ متعلق به عملیات ایجاد Note است و باید برای همه ورودی‌ها یکسان اجرا شود.

تکرار domain rule در endpoint و importer ضروری نیست؛ هر دو داده تبدیل‌شده را به Service می‌دهند. validation سریع در UI یا API ممکن است برای پیام بهتر اضافه شود، اما مرجع نهایی invariant همچنان Service است.

## قرار دادن invariant در Entity

انتخاب یادگیرنده: قانون عنوان در Note قرار گیرد، چون موجودیت نباید بتواند در وضعیت نامعتبر ساخته یا تغییر داده شود. این انتخاب با rich domain model سازگار است. شرط صحت آن بستن همه راه‌های دور زدن است: constructor یا factory و متد Rename باید یک تابع normalization/validation مشترک را صدا بزنند و Title setter عمومی نباشد. Service همچنان عملیات را هماهنگ می‌کند و قواعدی را که به کاربر، زمان یا storage وابسته‌اند اعمال می‌کند.
